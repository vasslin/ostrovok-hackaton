# «О!дин запрос» — AI-агент для планирования поездок

Прототип для Ostrovok Hackathon 2026. Цель — превратить сообщение путешественника в понятный план поездки: понять запрос, уточнить только критичные пробелы, предложить и сравнить варианты, проверить стыковки и довести до имитации бронирования.

## Что есть в репозитории сейчас

- Контракт `TripRequest`, валидация дат и ограничений, схемы JSON и примеры запросов.
- Реестр провайдеров и сборка HTTP-запросов по конфигурации.
- Локальный `TripRequest → TripPlan` с отдельными наборами запросов для поиска кодов и поиска предложений; для него нужны уже проверенные коды и даты заселения.
- Описания провайдеров и сохранённые ответы для офлайн-разработки.
- Набор тестов для схем, конфигов, параметров и сборки запросов.
- Сценарии сквозной приёмки и шаблон отчёта — см. ниже.

Исходный commit `33be312` содержал схемы, примеры, валидацию и построение запросов из **уже заполненного** конфига конкретной ручки. В текущей незакоммиченной рабочей копии добавлены `providerkit`, `BuildTripPlan`, CLI `cmd/maptrip` и проверки реестра/HTTP-запросов. `BuildTripPlan` возвращает `Discovery`, `Search`, `Missing` и `Limitations`; он не выполняет HTTP-вызовы и не разрешает названия городов в коды сам. Отельные предпочтения остаются в `TripRequest`, но гостиничный mock удалён и реальный отельный API не подключён. Преобразование свободного текста, нормализация ответов и сквозная интеграция ещё не составляют единый путь. Досуг у пересадок требует отдельной проверки времени пути и часов работы.

Ветка `providers-api` содержит провайдерный слой и не включает приложение. В `origin/frontend` есть отдельная автономная JS-демоверсия интерфейса и тесты UI-модели; её описание и контракт лежат в `frontend/README.md` и `frontend/docs/api-contract.md` на этой ветке. `origin/ai-service` содержит отдельную реализацию извлечения конфига и ранжирования отелей. Ветки не объединены. Последняя `origin/main` содержит каркас микросервисов, у которого бизнес-логика пока состоит из заглушек. Настоящая связка AI, интерфейса, провайдеров и серверного хранения не подтверждена. Данные и ответы помечайте по происхождению: реальные, кэшированные или синтетические.

## Быстрый старт текущего Go-модуля

Требуется Go 1.26 или новее.

```sh
go test ./...
go vet ./...
```

`go run ./cmd/smoke` отправляет запросы к реальным API и требует действующие ключи из локального `.env`; запускать его нужно отдельно от офлайн-тестов. Не добавляйте секреты в репозиторий.

Для локальной проверки маппинга без сетевых вызовов:

```sh
go run ./cmd/maptrip -trip configs/examples/trip_request.kazan_weekend.json -resolved configs/examples/resolved_trip.kazan_weekend.json -now 2026-10-27
```

Выход команды показывает запланированные `Discovery`/`Search` запросы, недостающие коды/поля и ограничения источников. Это не подтверждение наличия билетов или гостиничного тарифа.

## Проверка сценариев

Перед защитой пройдите сценарии из [матрицы тестирования](docs/TEST_SCENARIOS.ru.md). В README оставляйте фактический статус последнего прогона, дату, коммит и доказательства. Статусы: `не запускался`, `пройден`, `не пройден`, `заблокирован`. Не называйте сценарий пройденным, пока он не проверен на актуальной сборке.

### Целевой путь для сквозного демо

Последовательность ниже описывает критерий защиты после интеграции. Её нельзя считать пройденным тестом текущей ветки.

1. Пользователь пишет: «Хочу к тёплому морю в ноябре, недорого, с ребёнком, вылет из Москвы».
2. Агент показывает, что понял, явно отмечает предположения, задаёт только вопрос, без ответа на который нельзя сравнить варианты.
3. Агент предлагает направления с погодой, временем в пути и полной оценкой стоимости; синтетические цены подписаны.
4. Пользователь выбирает направление и получает сравнение транспорта, отелей и трансфера с причинами, компромиссами и рисками.
5. Агент проверяет даты, местное время прибытия, заселение и трансфер, собирает план и показывает итоговую сумму.
6. Пользователь меняет даты или бюджет; агент показывает, что пересчитано и что сохранено.
7. Перед имитацией оплаты агент обновляет цену/наличие и просит подтвердить изменившиеся условия. Повторное нажатие не создаёт второе бронирование.
8. После подтверждения отображаются статус и идентификатор демо-заказа; нигде не запрашиваются и не сохраняются реальные платёжные данные.

Подробные позитивные, негативные и граничные сценарии, ожидаемый результат и критерии зачёта находятся в [docs/TEST_SCENARIOS.ru.md](docs/TEST_SCENARIOS.ru.md).

### Краевые случаи, обязательные для показа

- **Неполный/размытый ввод:** неизвестное направление, месяц без точной даты, нет города вылета, неоднозначный бюджет; агент задаёт только нужное уточнение и показывает допущения.
- **Невозможные даты и ограничения:** дата в прошлом, выезд раньше возвращения, ночной перелёт, местные часовые пояса, прибытие после check-in; поиск и итоговая сборка блокируют несовместимый план.
- **Состав поездки:** ребёнок 0/17/18 лет, превышение вместимости номера, питомец, доступность или аллергия; не подтверждённые источником условия не выдумываются.
- **Пустые/ошибочные данные:** невалидный ответ AI, нет вариантов, неоднозначный геокодинг, провайдер вернул 401/429/5xx/таймаут/невалидный ответ, устарел кэш; агент показывает ошибку нужного сегмента и безопасное восстановление.
- **Границы провайдеров:** авиа, ЖД и водный транспорт, отсутствие цены у расписания, разные валюты и единицы тарифа, пустая гостиничная выдача; неизвестные значения не заменяются нулём или неподписанным mock.
- **Смена условий:** другие даты, бюджет, город или питомец; сохраняются совместимые варианты, неподходящие сбрасываются с объяснением, сумма пересчитывается.
- **Покупка:** новая цена при prebook, истёкший тариф, повторный запрос, задержка статуса, отмена; цена подтверждается до mock checkout, дубликат/ложный успех не создаётся.
- **Безопасность и честность:** чужой `user_id`/`order_id`, произвольный Origin, секреты/персональные данные в логах, внедрённый HTML/инструкция в данных, синтетические цены и отзывы; доступ ограничивается, ввод экранируется, маркировка данных видна.

Все перечисленные случаи описаны по ID в матрице. Там пока указано `не запускался`: сквозных ручных прогонов не было. При попытке проверить отсутствующий backend/UI-путь фиксируйте `заблокирован` с причиной, а не `пройден`.

## Отчёт и метрики

Используйте [шаблон отчёта](docs/REPORT_TEMPLATE.ru.md). В нём есть таблица соответствия пунктам ТЗ, протокол запуска, учёт реальных/кэшированных/синтетических данных и определения метрик. Минимально фиксируйте долю завершённых сценариев, соблюдение жёстких ограничений, число уточнений, время до первой полезной рекомендации, ошибки стыковок, изменение цены при повторной проверке и восстановление после ошибки провайдера.

Не публикуйте придуманные ответы как результаты реального опроса или реальные отзывы. Для макета допустимы синтетические примеры, но каждый экран, подпись и набор данных должны явно говорить «синтетические данные»; для продуктовых выводов соберите настоящие ответы с согласием участников.

## Текущая приёмка провайдерного кода

В текущей незакоммиченной копии 2026-10-27 проходят `go generate ./...`, `go test ./...`, `go vet ./...` и `git diff --check`. Лишняя пустая строка в `testdata/travelpayouts_places/places2.json` исправлена локально. Исторические ветки `origin/main` и `origin/providers-api` при трёхстороннем merge конфликтуют в `.env.example` и `.gitignore`; рабочая копия содержит объединённые варианты этих файлов, но merge ещё не проводился. Публичный пакет `providerkit` позволяет другому модулю импортировать типы провайдеров, но его подключение в `provider-service` и согласование workspace/протоколов остаются открытыми.

На `origin/frontend` 2026-10-26 добавлена независимая демоверсия: интерфейс использует локальные моковые данные и хранение в браузере; чат принимает ограниченный набор команд. Её заявленные тесты не запускались в рамках этой проверки. Контракт frontend рассчитан на gateway API, содержит суммы в копейках, `revision`, ошибку 409 и `Idempotency-Key`; при интеграции нужно согласовать эти поля с `TripRequest` и провайдерными моделями.

На `origin/ai-service` 2026-10-26 добавлены HTTP/gRPC ручки извлечения параметров поездки и ранжирования отелей через OpenAI-совместимый API (по умолчанию Groq). Ветка использует отдельный protobuf `travel.v1.TravelAI` и отдельную плоскую модель конфига, тогда как `origin/main` ожидает `godnota.ai.v1.AIService`, а provider-ветка описывает вложенный `TripRequest`. Трёхсторонняя проверка merge `ai-service` с `origin/main` выявляет конфликты в семи файлах: `.env.example`, `.gitignore`, AI Dockerfile/Go module/app и корневом `docker-compose.yml`.

Трёхстороннее объединение `frontend` с `origin/main` не даёт текстовых конфликтов, но API контракты логически несовместимы. На `origin/main` файл `.env` отслеживается Git и `.gitignore` не исключает `.env`; проверенный файл содержит адреса сервисов, не API-ключи. До добавления ключей нужно исключить `.env` из Git и проверить историю на секреты.

`origin/task_info` уже вошла в `origin/main` (PR merge commit `cb9ff40`). Локальная ссылка `main` обновлена до `origin/main` (`b767205`); активная рабочая копия остаётся на `providers-api`, поэтому файлы разных веток здесь сравниваются через Git, без переключения и merge.

В backend-каркасе `origin/main` нет Go-тестов; контроллеры/заглушки возвращают пустые ответы и местами игнорируют ошибки usecase. Gateway и gRPC-логирование записывают полные тела сообщений/запросов. Gateway CORS отражает произвольный Origin, а маршруты профиля/заказа принимают идентификаторы пользователя/заказа без проверки авторизации. Не подключайте реальные профили к этому каркасу до реализации аутентификации, авторизации и безопасного логирования.

В `origin/ai-service` ключ сервисной авторизации необязателен, для `LLM_BASE_URL` разрешён HTTP, а внешние ручки API открываются напрямую из Compose. Перед общим доступом нужна обязательная сервисная авторизация, HTTPS для провайдера, ограничения квот/частоты и закрытая внутренняя сеть. Извлечение конфигурации ограничено двумя вопросами, но текущая реализация не создаёт варианты направлений при пустом destination.
