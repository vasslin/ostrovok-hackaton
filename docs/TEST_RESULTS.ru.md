## Интеграционные сценарии

- session-service: protobuf/gRPC → usecase → repository; создание, сохранение контекста, история, владелец, отсутствующий id, отмена.
- map-service: реальный gRPC, типы JSON, поля гостиницы/гостей/валюты, недостающие коды, невалидный конфиг.
- provider-service: gRPC → реальный локальный TLS HTTP-сервер поставщика; запрос, credentials в нужном месте, нормализация кэшированной цены, частичный 429, retryable, отсутствие утечки ключей.
- gateway: реальный gRPC-диспетчер и JSON-контракт, включая int64 цены строкой; HTTP-регистрация/login/logout, ротация токена, лимиты, неправильные тела, подмена идентификаторов, доступ к чужим ресурсам.
- auth storage: reload, срок токена, соль/хеш вместо пароля, сбои записи и откат изменений, конкурентная регистрация одного email.
- planning: подтверждение, сброс кэша, ошибки backend, невалидный конфиг, копирование результатов, передача transport/hotel/errors в route-service, сохранение частичной выдачи при неготовности этапа 3.

## Backend E2E

Тесты сами собирают и запускают 6 сервисов на свободных портах. После завершения созданные процессы останавливаются; данные тестов отделены от пользовательского локального запуска.

1. **demo authenticated lifecycle and ownership** - регистрация, повторная регистрация, неправильный и правильный login, отзыв старого токена, сессия, маппинг, сохранение/чтение/подтверждение конфига, 4 транспорта + 1 гостиница, явный статус неготовности этапа 3, чужой пользователь, параллельные запросы, сброс выдачи после правок, logout.
2. **live missing credentials preserves explicit provider errors** - live без ключей возвращает пустые предложения и структурированные ошибки, не заменяет их синтетическими.
3. **portable smoke command** - та же функция, которую вызывает общая команда `go run ./cmd/dev smoke`, проходит весь демонстрационный путь через публичный API.

Это API E2E, не браузерный E2E: интегрированного frontend в этой ветке нет. Внешние travel API тестами не вызываются. Тесты протокола с локальным сервером не являются проверкой доступности реального поставщика.

## Полнота части

- Авторизация и права доступа - реализованы для прототипа с одним gateway и файловым хранилищем.
- Конфиг для нейронки и маппинг - реализованы, включая сохранение требований и независимую валидацию.
- Этап 2 (поиск частей маршрута) - реализован и воспроизводимо проверен с demo и HTTP-адаптерами. Передача частей в route-service теперь подключена.
- Полная live-интеграция **ещё не готова**: нет реального гостиничного адаптера, автоматического геокодинга, проверки с реальными ключами. Это явно возвращается в ошибках/ограничениях.
- Вызов LLM по свободному тексту, склейка и ранжирование, frontend и покупка - другие этапы/ветки, не заявлены как работающие. `route-service.BuildRoutes` честно возвращает Unimplemented до реализации этапа 3.
