# План дальнейшей работы

Основание: ABOUT.md, прежде всего этапы обработки запроса в разделе 2, ответственность сервисов, двухэтапное ранжирование в разделе 7.3, хранение контекста и критерий готовности MVP в конце документа. План продолжает текущую реализацию, а не начинает её заново.

## Текущее состояние

- Работают реальный локальный Qwen, заполнение конфига, уточнения и сохранение контекста через session-service.
- Проверены Makefile, Go-тесты, race detector, vet, frontend-тесты, нативный запуск и полный Docker-стек.
- Ключи транспорта проверены: для Москвы — Парижа на 4–11 ноября 2026 получены ответы Travelpayouts и Яндекса. Через backend получены 50 транспортных частей и до 20 кандидатов, без синтетической подмены.
- В этом live-прогоне коды городов были явно получены из справочников и переданы в resolved. Теперь обычный поиск автоматически получает коды через справочники; проверено без ручного PATCH с resolved.
- Два транспортных ключа не подключают поиск отелей. AI-ранжирование доступно отдельными методами, но основной сценарий пока использует детерминированную сортировку route-service.

## 1. Устранить блокер live-поиска: автоматический resolved

Реализовано: provider-service получает коды через справочники, возвращает resolved в SearchPartsResponse; travel-service сохраняет их в сессии и исключает из обращений к AI. При изменении городов соответствующие коды сбрасываются. Ошибки разрешения возвращаются отдельно, включая clarification_required для неоднозначного названия. Подтверждение пользователя и отображение уточнений в форме относятся к следующим пунктам плана.

Приоритет: P0. Основные компоненты: provider-service, map-service, travel-service, session-service.

1. Определить контракт получения и возврата проверенных кодов городов. Внешние HTTP-запросы остаются в адаптерах provider-service; travel-service только организует последовательность.
2. По названиям и стране получать IATA-коды и координаты через Travelpayouts places2; затем коды Яндекса через nearest_settlement.
3. Не выбирать город по первому результату или служебному весу. При неоднозначности вернуть уточнение страны/города пользователю.
4. Хранить проверенный resolved отдельно от пожеланий request. Передавать его маппингу и поиску, сохранять в сессии; не отправлять модели.
5. Кэшировать результаты с TTL и соблюдать RPS из configs/providers.json. Предусмотреть тайм-аут, отмену и частичное разрешение кодов.
6. При смене направления сбрасывать устаревшие коды и результаты. Изменение бюджета не должно приводить к лишним запросам к справочникам, если города остались прежними.

Критерий готовности: обычный запрос «Москва — Париж» проходит от чата до live-результатов без ручного PATCH с resolved; неоднозначный город вызывает вопрос, а не поиск по случайному коду. Отдельные тесты проверяют смену направления, кэш, отказ справочника и отсутствие внешних вызовов в demo-режиме.

## 2. Вернуть явное подтверждение конфига перед поиском

Реализовано: редактируемая карточка, отдельное сохранение и подтверждение поиска, восстановление вопросов/ответов и лимит раундов. См. docs/STEPS_1_3.md.

Приоритет: P0. Основные компоненты: frontend, travel-service, ai-service.

1. После generate показывать редактируемый конфиг, включая город отправления, направление, даты, гостей, бюджет и необходимость отеля.
2. Разделить готовность конфига и согласие пользователя на поиск. Убрать автоматический вызов confirm из обработки каждого готового AI-ответа.
3. При короткой реплике вроде «хочу в Париж» использовать известный контекст, но показать унаследованные даты и состав гостей перед подтверждением.
4. Вопросы отображать отдельными полями; ответы отправлять упорядоченным массивом с question_id. Сохранять возможность исправить предыдущий ответ.
5. Соблюдать лимит уточнений N из ABOUT.md, не заполняя неизвестные обязательные поля вымышленными значениями.

Критерий готовности: до нажатия «Подтвердить и искать» провайдеры не вызываются; правки сохраняются, прежняя выдача инвалидируется, а вопросы и ответы восстанавливаются из сессии.

## 3. Сделать понятным поиск без гостиничного провайдера

Реализовано: API возможностей, явный выбор транспорта без отеля, понятные состояния ошибок и частичные цены. Живой гостиничный поиск требует предоставленного партнёрского доступа; доступных учётных данных нет. См. docs/STEPS_1_3.md.

Приоритет: P0. Основные компоненты: provider-service, travel-service, frontend.

1. Показывать возможности настроенных провайдеров. Отдельно различать отсутствие гостиничного API, ошибку API и отсутствие подходящих отелей.
2. Если отель нужен, предложить подключить провайдера или явно выбрать поиск только транспорта. Не отключать отель молча и не подставлять синтетику в live.
3. При подключении Hotelbeds/RateHawk отдельно проверить авторизацию, даты, гостей, комнаты, отмену и область тарифа. Evaluation/sandbox не обозначать как реальную доступность.
4. Заменить технические пути и английские сообщения на понятные пользовательские состояния. Детальные коды сохранить для диагностики.
5. Частичные результаты маркировать явно: транспорт найден, проживание не подобрано, общая цена поездки не подтверждена. Не показывать неизвестные трансферы и активности бесплатными.

Критерий готовности: при двух транспортных ключах пользователь получает понятный результат и выбор дальнейшего действия вместо списка /resolved/... и сообщения No live hotel API configured.

## 4. Подключить двухэтапное AI-ранжирование из ABOUT.md

Приоритет: P1. Основные компоненты: route-service, ai-service, travel-service.

1. Зафиксировать параметры k, m, threshold и общий бюджет LLM-вызовов/времени на сценарий.
2. Route-service формирует k совместимых склеек по городам, датам и времени. Несовместимые сочетания исключаются кодом до обращения к модели.
3. Для каждой склейки вызывать RankJoinOptions с контекстом и реальными предложениями; возвращать до m вариантов.
4. Объединять до k*m кандидатов, удалять дубликаты и повторно проверять ограничения.
5. Travel-service вызывает RankFinalRoutes для сравнения кандидатов между собой и возвращает верхние threshold результатов.
6. Добавить краткие объяснения оценок и различий. Цены и итоговые суммы вычислять кодом; модель не создаёт новые ID, тарифы или подтверждения наличия.
7. При недоступной модели возвращать явно отмеченную детерминированную выдачу либо понятную ошибку, согласно согласованному режиму. Не выдавать запасную сортировку за AI-оценку.

Критерий готовности: трасса реального запроса содержит оба этапа ранжирования; все возвращённые ID принадлежат входным предложениям, соблюдаются лимиты и deadline. Есть тесты на выдуманные/повторные/пропущенные ID и частичный отказ модели.

## 5. Завершить итерации маршрута и контекст

Приоритет: P1. Основные компоненты: travel-service, session-service, frontend, map-service.

1. Проверить три сквозных сценария ABOUT.md: известные параметры, генерация 2–3 идей, изменение найденного маршрута.
2. Текстовые правки направлять в AI, изменения полей формы — структурированным обновлением.
3. При правке дат/направления перепроверять затронутые предложения и сбрасывать несовместимый выбор. Показывать, что изменилось относительно предыдущей выдачи.
4. Перед каждым запросом загружать контекст и конфиг; после успешной обработки сохранять новые сообщения, summary и актуальный конфиг без дублирования истории.
5. Добавить версию состояния или иной контроль конкурентных изменений, чтобы два параллельных запроса не затирали друг друга.
6. Постепенно перенести преобразование маршрутов в единый DTO frontend в map-service, чтобы frontend не собирал бизнес-маршрут из несогласованных частей самостоятельно.

Критерий готовности: смена дат, направления, гостей и бюджета проходит без потери остальных пожеланий, старых цен и чужих предложений; повторные и параллельные сообщения обработаны предсказуемо.

## 6. Довести заказы до критерия MVP

Приоритет: P1. Основные компоненты: order-service, gateway, frontend, session-service.

1. Сохранять неизменяемый снимок выбранного маршрута и связь с владельцем.
2. Завершить имитированный цикл создания, оплаты и отмены, с идемпотентностью и проверкой допустимых переходов статусов.
3. Подключить эти операции к интерфейсу, включая обработку повторного нажатия и ошибок.
4. Реализовать серверную историю заказов, доступную после входа с другого устройства. Текущие ссылки в localStorage одного браузера не заменяют её.
5. Определить, какие данные должны переживать перезапуск; не полагаться на память процесса для подтверждения конфига, заказов и истории.
6. Реальные резервирования и платежи вынести за пределы демо-MVP: для них нужны отдельные адаптеры, повторная проверка цены и компенсация частичного успеха.

Критерий готовности: пользователь проходит демобронирование, оплату и отмену без дублей и потери контекста; другой пользователь не может получить или изменить заказ.

Приоритет: P1, выполнять параллельно с предыдущими пунктами.
