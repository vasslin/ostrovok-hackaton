# API: этап 2, авторизация и конфиги

HTTP/gRPC-контракты поиска частей маршрута, авторизации и конфигурации поездки. Поиск соответствует разделу «Этап 2: Поиск частей маршрута» в ABOUT.md.

## Соответствие заданию

| Требование | Реализация |
|---|---|
| Проверить готовность конфига | `providerkit.ValidateSearch`, независимая проверка перед подтверждением и перед вызовами источников |
| Единый конфиг нейронки | Существующий `TripRequest` сохранён: `configs/trip_request.schema.json`; добавлена схема ответа AI |
| Маппинг провайдерам | `providerkit.MapConfig`, gRPC `MapService.MapToProviderConfigs`, HTTP `POST /api/providers/map` |
| Поиск частей маршрута | Новый gRPC `ProviderService.SearchParts`; travel-service получает и возвращает `parts` |
| Параллельные вызовы | Вызовы транспорта и гостиничного адаптера запускаются параллельно; частичный сбой не уничтожает соседние результаты |
| Нормализация | Типизированные protobuf `TransportPart`, `HotelPart`, `Money`, `ProviderError` |
| Ошибки/пустая выдача | Отдельный массив `errors`, пустые массивы предложений, ошибки таймаута/HTTP/формата/конфигурации |
| Авторизация | Register/login/me/logout; Bearer-токен; доступ к ресурсам проверяется до целевого backend-вызова |
| Хранение контекста поиска | Рабочий session-service; конфиг и подтверждение сохраняются, изменение сбрасывает старую выдачу |

Выход этапа 2 - отдельные части, не готовые маршруты. `travel-service` передаёт их в `route-service.BuildRoutes(session_id, config, parts)` и возвращает совместимые кандидаты в `candidates` наряду с `parts`. При ошибке сборки части сохраняются, а причина добавляется в `limitations`. Детерминированная сборка работает; AI-ранжирование, многогородные маршруты и пересадки между предложениями пока не реализованы. [Контракт маршрутов](route/README.md).

## Запуск на macOS, Linux и Windows

Одинаковая команда для всех ОС, Go 1.26.5:

```text
go run ./cmd/dev run
```

Собираются и запускаются шесть сервисов нашей части. Ctrl+C останавливает их. Проверка уже запущенного API: `go run ./cmd/dev smoke`. Для свободных портов - `go run ./cmd/dev run -random-ports`. Для live - `go run ./cmd/dev run -mode live`, ключи в локальном `.env` либо окружении. PowerShell/Bash/Python/protoc для запуска не требуются.

Docker: `docker compose up --build --wait` при запущенном Docker Engine/Desktop и Compose 2.24+. Подробная настройка, диагностика и различия native/Docker - в [GUIDE.ru.md](GUIDE.ru.md).

## Авторизация

Регистрация:

```http
POST /api/auth/register
Content-Type: application/json

{"email":"participant@example.com","password":"example-long-password"}
```

Ответ 201: `user {id,email}`, `access_token`, `token_type=Bearer`, `expires_at`. Для входа - тот же JSON на `POST /api/auth/login` (200). Остальные `/api` ручки требуют:

```http
Authorization: Bearer <access_token>
```

- `GET /api/auth/me` - текущий аккаунт.
- `POST /api/auth/logout` - отзыв токена, ответ 204.
- Токен действует 24 часа. Новый login отзывает предыдущий токен этого аккаунта.
- Пароль: не менее 12 символов, не более 128 байт. Случайная 16-байтная соль, PBKDF2-SHA256 / 600 000 итераций, сравнение за постоянное время.
- В `data/auth.json` находятся хеши паролей и SHA256 токенов. Запись через временный файл, синхронизацию и переименование. Текст пароля и исходный токен не записываются.
- Хранилище рассчитано на один gateway-процесс; несколько реплик требуют общего хранилища с транзакциями.
- Ограничение login/register: 10 попыток в минуту на адрес соединения. Прокси-заголовкам `X-Forwarded-For` gateway не доверяет.
- `POST /api/sessions` принимает `{}`. Владелец берётся из токена. Подмена `user_id` даёт 403; чужая сессия или заказ - 404; без токена - 401.
- `GET/PATCH /api/users/{user_id}` разрешены только для собственного id. Сам user-service пока содержит исходные заглушки; полноценный аккаунт доступен через `/api/auth/me`.
- Ресурсные идентификаторы принимаются в snake_case; camelCase-алиасы отклоняются, чтобы не обходить проверки protobuf JSON.
- CORS использует `CORS_ALLOWED_ORIGINS`, а не отражает произвольный Origin. По умолчанию разрешены localhost:8080, 127.0.0.1:8080 и localhost:5173.

Документация и `/health` публичны. Для доступа через интернет перед gateway нужен HTTPS. Внутренние gRPC-сервисы доверяют внутренней сети; наружу их публиковать не следует.

## Конфиг и поиск через HTTP

Создайте сессию: `POST /api/sessions` с `{}`. Сохраните полный конфиг:

```http
PATCH /api/sessions/<session_id>/config
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "config": {
    "version": "1.0",
    "request": {
      "schema_version": "1.0",
      "locale": "ru",
      "currency": "RUB",
      "origin": {"city": "Москва"},
      "destination": {"city": "Казань"},
      "dates": {"departure_date": "2026-12-12", "return_date": "2026-12-14", "nights": 2},
      "travelers": {"adults": 2},
      "transport": {"modes": ["train", "plane"], "round_trip": true, "direct_only": true},
      "hotel": {"needed": true, "rooms": 1, "star_rating_min": 3, "meal": "breakfast"}
    }
  }
}
```

Эта PATCH-ручка заменяет объект конфига целиком; это не JSON Merge Patch. Для изменения одного поля загрузите текущий `GET .../config`, измените поле и отправьте полный объект.

Далее `POST .../confirm` с `{}`, затем `POST .../search` с `{}`. `GET .../routes` возвращает последнюю выдачу текущего подтверждённого конфига. Изменение конфига делает её недоступной и требует повторного подтверждения. Одновременные операции одного planning-controller над одной сессией сериализуются.

Поиск требует точной даты и выбранного направления; неизвестный месяц без дня не заменяется случайной датой. Проверяются типы, неизвестные поля, диапазоны, дата в прошлом, последовательность дат и продолжительность. Для пребывания/обратного пути нужны return_date либо nights. Цены этапа 2 поддерживают RUB, USD и EUR; валюты с другим числом минимальных единиц не конвертируются молча.

`config.request` - тот же JSON `TripRequest`, который передаётся нейронке и CLI `cmd/maptrip`. `version/trip` исходного protobuf сохраняется для совместимости простых запросов. Одновременное указание `request` и `trip` запрещено. Legacy-параметры, которые нельзя перенести без потери смысла, отклоняются с просьбой использовать `request`.

Статусы ответа AI: `advice`, `questions`, `generate`. Во время уточнений config может быть частичным; окончательный поиск всегда валидируется backend независимо от статуса модели. Условия вроде «заполнено >40%» не обходят обязательные поля и подтверждение пользователя. Само подключение LLM и диалоговый цикл относятся к отдельной ветке команды.

## Маппинг

```http
POST /api/providers/map
Authorization: Bearer <access_token>
Content-Type: application/json

{"config": <TripRequest>, "resolved": <ResolvedTrip>}
```

Ответ: `configs[] {provider,endpoint,params}`, `missing[]`, `limitations[]`.

Пример проверенных кодов из `configs/examples/resolved_trip.kazan_weekend.json`:

```json
{
  "origin": {"iata": "MOW", "yandex_code": "c213", "latitude": 55.7558, "longitude": 37.6173},
  "destination": {"iata": "KZN", "yandex_code": "c43", "latitude": 55.7987, "longitude": 49.1059}
}
```

В конфиге сессии этот объект передаётся как `config.resolved`. Коды не извлекаются из догадок LLM. Контракт предполагает, что вызывающий backend проверил их соответствие городам; формат валидируется повторно. Автоматический геокодинг и разрешение неоднозначных названий в эту интеграцию не включены; без кодов live возвращает missing_field для соответствующих источников.

Для гостиниц сохраняются даты, гости/возраст детей, питомцы, номера, звёзды, питание, отмена, бюджет за ночь, тип/удобства/расположение, ранний заезд/поздний выезд. Неиспользованные источником предпочтения нельзя считать выполненными. Demo явно возвращает предупреждения о неподтверждённых условиях.

## Формат выдачи и провайдеры

`parts`: `transport_parts[]`, `hotel_parts[]`, `errors[]`, `limitations[]`.

Каждая часть содержит id, provider, source (`synthetic` / `cached` / `live`), fetched_at. Транспорт содержит даты и время RFC3339 с часовым поясом, коды отправления/прибытия, названия городов и пересадки. У Aviasales round-trip содержит также return_departure_at/return_arrival_at; единая цена относится к обеим поездкам. Нельзя отдельно суммировать её второй раз за обратный путь.

`price.amount_minor` - int64 в минимальных единицах валюты; protobuf JSON отдаёт его **строкой**. `price.scope`: `per_person_one_way`, `per_person_round_trip`, `stay_all_rooms`. Отсутствие price означает неизвестную цену, а не 0. Состав группы не масштабируется по взрослому тарифу без подтверждения детских тарифов поставщиком.

- **demo**: генерирует предложения для заданных городов и дат, не выполняет сетевые вызовы. Все цены/гостиницы синтетические. Указанные часы UTC иллюстративные.
- **live/Aviasales**: кэшированные цены, не подтверждение мест. Отправляются нужные даты/коды/валюта/прямой рейс; после нормализации применяются ограничения по числу пересадок, времени выезда и длительности.
- **live/Яндекс.Расписания**: прямые сегменты и составные маршруты с описанными отдельными рейсами; стоимость и наличие не подтверждаются. Route-service проверяет время ожидания и совпадение кодов станции, несовместимые стыковки отклоняет. Смена станции без подтверждённого переезда не поддерживается. Сохраняется атрибуция Яндекса.
- **live/hotel**: при настройке возвращаются предложения Hotelbeds evaluation или RateHawk с источником, предупреждениями и явными ошибками при недостатке данных. Hotelbeds evaluation не подтверждает реальную доступность; в demo используются синтетические варианты.

HTTP-ответы внешних API ограничены 4 MiB, вызовы - таймаутом до 4 секунд и настройками реестра. Redirect отключён, чтобы не пересылать credentials другому адресу. RPS общий для экземпляра searcher. Повторы автоматически не выполняются. 429/5xx помечаются retryable, причины сбоя не содержат тела ответа или URL с ключами. Пустой валидный ответ отличается от невалидного JSON/неожиданной структуры.

| Проверка | Результат |

| Docker Compose config | Пройдено; запуск контейнеров не подтверждён, daemon недоступен |
| Linux amd64/arm64, macOS Intel/Apple Silicon | Кросс-компиляция runner и шести сервисов пройдена; нативные тесты ожидают CI |
| Диалог с LLM, склейка маршрута, оплата | За границами этой части; исходные сервисы остаются каркасом |


Запуск тестов: `go run ./cmd/dev test -cover`. Интеграции включены в обычный прогон. Межпроцессный backend E2E: `go run ./cmd/dev e2e`. Проверка гонок: `go run ./cmd/dev test -race -cover` при наличии C-компилятора. Команды одинаковы для всех ОС. Покрытие и область подсчёта - `reports/coverage.md`; матрица CI проверяет Windows/macOS/Linux. Proto-код хранится в `pkg/generated`; для его повторной генерации нужны protoc и Go-плагины, команда `sh scripts/gen-proto.sh`.
