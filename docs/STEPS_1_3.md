# Шаги 1–3: подготовка и подтверждение поиска

Реализация следует разделам ABOUT.md о подтверждении конфигурации, упорядоченных ответах на уточнения и разделении ответственности сервисов.

## Пользовательский сценарий

1. Пользователь пишет пожелания. AI заполняет конфиг или задаёт вопросы отдельными полями. Ответы отправляются одним массивом с question_id в порядке вопросов.
2. Интерфейс показывает редактируемую карточку: города и страны, даты, взрослые и возраст детей, гражданство, бюджет, валюта, транспорт и необходимость отеля. Унаследованные параметры видны до подтверждения. Неизвестные обязательные значения пользователь вводит сам.
3. Сохранение правок не вызывает confirm или search. Ранее найденные варианты скрываются, backend сбрасывает подтверждение и кэш выдачи.
4. Поиск начинается после кнопки «Подтвердить и искать». Кнопка «Искать только транспорт» означает явное согласие убрать проживание из этого поиска; поле hotel.needed сохраняется как false.
5. В live коды городов получаются автоматически через provider-service и сохраняются отдельно в resolved. Модель не получает эти коды. Подробности в AUTO_RESOLVED.md.

## Возможности провайдеров

GET /api/sessions/{session_id}/capabilities доступен владельцу сессии и описан в OpenAPI gateway. Travel-service проверяет владельца и обращается к ProviderService.GetCapabilities. Ответ содержит режим, наличие транспортных ключей и статус гостиничного провайдера, без значений ключей. Статус available означает настроенный адаптер/учётные данные, а не подтверждённую доступность внешнего API.

Demo обозначается synthetic; Hotelbeds evaluation и RateHawk sandbox отображаются как тестовые среды. Транспортные ключи не включают гостиничный API. Для подключения гостиничного поиска оператору нужны партнёрские учётные данные и режим из .env.example; затем нужно пересоздать provider-service. Подключать новый аккаунт или обещать реальное наличие без предоставленного партнёрского доступа сервис не пытается.

При отсутствии гостиничного API интерфейс предлагает явно выбрать только транспорт. Отель не отключается автоматически. Отсутствие настройки, ошибка провайдера и отсутствие подходящих отелей различаются. Частичные результаты помечаются; неизвестная стоимость проживания, трансферов и развлечений не отображается нулевой. Бронирование доступно только для маршрута с backend route_id.

Технические коды и исходные сообщения остаются в parts.errors для диагностики, а интерфейс показывает объяснения на русском. Код clarification_required предлагает уточнить город и страну в карточке.

## Восстановление и ограничение уточнений

После перезагрузки интерфейс восстанавливает конфиг, вопросы и ответы из session-service. Для событий изменения конфига сохраняется маркер config_updated, чтобы старые вопросы не показывались как текущие. Сохранённая выдача запрашивается отдельно; при отсутствии актуальной выдачи остаётся карточка подтверждения.

MAX_CLARIFICATION_ROUNDS ограничивает число раундов с вопросами, по умолчанию 3. После лимита новые вопросы не добавляются; интерфейс предлагает заполнить карточку. Лимит не превращает неизвестные значения в вымышленные и не обходит финальную backend-валидацию.

## Проверка

- make test: тесты модулей и vet.
- make e2e: полный запуск, запрет поиска без подтверждения, поиск и инвалидирование выдачи, сценарий заказа, завершение дочерних процессов.
- Race-проверки изменённых backend-пакетов.
- 31 frontend-тест: отсутствие автоматического поиска, явное согласие на транспорт, единицы бюджета, частичные цены, восстановление вопросов и безопасные статусы провайдеров.

Запуск обновления: docker compose build provider-service travel-service gateway frontend; затем PROVIDER_MODE=live docker compose up -d --no-deps provider-service travel-service gateway frontend. Нативно — make MODE=live. После обновления интерфейса перезагрузите страницу.
