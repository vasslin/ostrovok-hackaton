# Что сделано: провайдеры путешествий и конфиги

**Ostrovok Hackathon 2026 · трек «О!дин запрос» · команда godnota**
Задача 2 (Даня Антонов): найти API провайдеров путешествий (билеты, отели, досуг во время поездки и пересадок), подготовить конфиги и описание API.
Дата: 2026-10-25. Ничего не закоммичено: все файлы лежат в рабочей копии ветки `agent`.

- Проверили реальными запросами 17 API: что работает, что требует ключа, что умерло.

## 3. Как устроены конфиги

```
текст пользователя ─► ai-service заполняет TripRequest (только «человеческие» значения)
                                     │ проверка по схеме → missing_required
                                     ▼
travel-service ─► provider-service
                    1. Resolver: город → IATA, код Яндекса, координаты, часовой пояс
                    2. Builders: TripRequest → map[провайдер][]Request
                    3. Клиент: HTTP по providers.json (авторизация, лимиты, кэш)
                    4. Нормализация ответов → TransportOption / HotelOffer / LeisureItem
```

**Главное правило: AI заполняет только понятные человеку значения** (названия городов, даты, количество людей, пожелания). Коды провайдеров (`KZN`, `c213`, id отелей) вычисляет Go-код, поэтому модель не может их выдумать.

**Правило с доски «> незаполненных полей — через агента, < — сами»:** бэкенд заполняет `completeness.missing_required` списком путей (например `/origin/city`). Если пустых полей много, спрашивает агент; если мало, фронтенд показывает короткую форму.

### 3.1. Единый конфиг для AI-агента: `TripRequest`

Файл схемы: `configs/trip_request.schema.json`.

**Обязательные поля:**
- `schema_version`, `locale`, `currency`;
- `origin.city`;
- `dates` (`departure_date` **или** `departure_month`);
- `travelers.adults`.

**Остальные блоки:**
- `destination`: город или кандидаты. Пусто — режим вдохновения.
- `dates`: даты, число ночей, гибкость.
- `travelers`: взрослые, возраста детей, питомцы, гражданство.
- `transport`: виды транспорта, прямые рейсы, пересадки, время вылета.
- `hotel`: звёзды, питание, бесплатная отмена, цена за ночь, удобства, расположение.
- `leisure`: интересы, досуг на пересадках.
- `budget`.
- `ai_context`: «доп поле для валидации — определяет ИИ»: цель поездки, прогулочный район, события, must have / must avoid, допущения агента.

### 3.2. Конфиги для каждого API

1. **`configs/providers.json`:** реестр. Для каждого провайдера:
   - базовый URL;
   - авторизация: только *имена* переменных окружения, секретов в файле нет;
   - лимит запросов в секунду, таймаут, время кэша;
   - для каждой ручки: метод, путь, где параметры (`query` или `json`).
2. **`configs/examples/<провайдер>.<ручка>.json`:** конфиг запроса: ровно те параметры, которые уходят в HTTP-запрос, с именами полей как у провайдера.
3. **В коде:** `RequestSet map[string][]Request`, то есть «мапа [имя провайдера] → конфиг», как на доске. Значение — срез, потому что одному провайдеру может понадобиться несколько вызовов (туда и обратно, поиск → страница отеля).

### 3.3. Как помечены обязательные поля и ограничения формата

В самом JSON отметить обязательность нельзя. Поэтому:

- **Единственный источник правды — теги Go-структур:**
  ```go
  Origin string `json:"origin" url:"origin" validate:"required,len=3,alpha,uppercase" jsonschema:"required,pattern=^[A-Z]{3}$"`
  ```
  - `validate`: проверка в Go во время работы (библиотека go-playground/validator);
  - `jsonschema`: попадает в сгенерированную JSON Schema (библиотека invopop/jsonschema);
  - `url` / `json`: как поле отправляется (query-строка или тело JSON);
  - `path:"name"`: подставляется в `{name}` в пути ручки.
- **Схемы генерируются командой `go generate ./...`.** Их можно отдать:
  - Соне: LLM заполняет конфиг строго по схеме;
  - Василине: для описания ручек;
  - Дане Казановичу: форма для недостающих полей.
- **Правила, которые не выразить тегами**, написаны кодом:
  - `TripRequest.ValidateAt`: возвращение после отъезда, не больше 30 ночей, дата не в прошлом и не дальше 365 дней;
  - `HotelsSearchBase.Check`: выезд после заезда, не больше 30 ночей.

### 3.4. Шпаргалка по форматам провайдеров

| Что | Правило |
|---|---|
| Даты в запросах | `YYYY-MM-DD`; Aviasales принимает ещё `YYYY-MM` |
| Дата-время в ответах | ISO 8601 со смещением (смещение не терять!), отмена в ETG — UTC |
| IATA | 3 заглавные буквы `^[A-Z]{3}$` |
| Коды Яндекса | город `c213` (Москва), станция `s9600213` |
| Страна | ETG `residency` строчными (`ru`), Travelpayouts `country_code` заглавными (`RU`) |
| Валюта | Aviasales строчными (`rub`), ETG заглавными (`RUB`) |
| Координаты | lat −90..90, lon −180..180; **в OSRM порядок `lon,lat`** |
| Гости в отеле | до 9 номеров; 1–6 взрослых на номер; до 4 детей 0–17 лет на номер |
| Проживание | заезд не позже чем через 730 дней; выезд не позже 30 дней после заезда |
| Хэши ETG | `hash` 1–256 символов, живёт 24 ч; `search_hash` живёт 38 мин; `partner_order_id` — UUID |
| Пагинация | Яндекс `limit` ≤100; Nominatim `limit` ≤40 |
| Погода | прогноз до 16 дней; морской прогноз 0–8 дней; история с 1940 (море с 2022) |

### Что проверяют тесты

- Каждый пример проходит и Go-теги, и свою JSON Schema, и превращается в правильный HTTP-запрос.
- URL собирается правильно для Aviasales (query + заголовок), Яндекса (ключ в query), OSRM (подстановка в путь), Википедии и для POST с JSON к отелям.
- 16 неверных значений отклоняются, например:
  - IATA строчными;
  - 7 взрослых в номере;
  - 5 детей в номере, ребёнок 18 лет;
  - проживание больше 30 ночей;
  - `residency` заглавными;
  - не-UUID в `partner_order_id`;
  - ребёнок-гость без возраста;
  - `limit` Nominatim больше 40.
- 11 ошибок в `TripRequest` отклоняются: возвращение раньше отъезда, дата в прошлом, 10 взрослых, неизвестный транспорт и т.д.
- `MissingRequired` возвращает правильные пути.
- `providers.json` совпадает с каталогом в Go.
- Схемы на диске актуальны: тест падает, если поменяли структуру и забыли `go generate`.

Отдельно проверено, что тесты действительно ловят ошибки. Если специально испортить пример (`"origin": "mow"`), падают обе проверки: схема (`'mow' does not match pattern '^[A-Z]{3}$'`) и теги Go.

## 5. Как пользоваться

Нужен Go 1.26+:

```bash
brew install go
```

После изменения любой структуры:

```bash
go generate ./...
```

Проверить всё:

```bash
go test ./...
```

Пример в коде:

```go
reg, _ := providers.LoadRegistry("configs/providers.json")
req, err := reg.NewHTTPRequest(ctx, providers.Request{
    Provider: "aviasales", Endpoint: "prices_for_dates",
    Params: &providers.AviasalesPricesForDates{Origin: "MOW", Destination: "KZN", DepartureAt: "2026-12-12", Currency: "rub"},
})
// req — готовый *http.Request
```

Секреты задаются переменными окружения:
- `TRAVELPAYOUTS_TOKEN`
- `YANDEX_RASP_API_KEY`
- `HOTELS_KEY_ID`, `HOTELS_KEY`

**Добавить новую ручку:**
1. Написать структуру с тегами в `internal/providers/`.
2. Добавить её в `Catalog`.
3. Добавить ручку в `providers.json`.
4. Положить пример в `configs/examples/`.
5. Выполнить `go generate ./...`, затем `go test ./...`.

## 6. Что ещё не сделано и на что обратить внимание

### Ключи и проверка настоящими запросами

Утилита `go run ./cmd/smoke` отправляет все примеры в настоящие API (ключи берёт из `.env`) и сохраняет ответы в `testdata/`. Секреты вычищаются и из вывода, и из файлов.

Прогон 2026-10-25:

| Провайдер | Результат |
|---|---|
| Aviasales (`prices_for_dates`) | ✓ 200, реальные рейсы Москва → Казань на 12–14 декабря |
| Travelpayouts places, Nominatim, OSRM, Open-Meteo (прогноз, история, море), ЦБ | ✓ 200 |
| Яндекс.Расписания | ✓ 200 со вторым ключом (первый так и не активировался). Поиск: 10 поездов Москва → Казань на 12 декабря, **ни у одного нет цены** — цены на поезда берём из `transport_mock`. Код Казани `c43` подтверждён. В `thread` время остановок приходит в другом формате: `2026-12-12 20:40:00`, без часового пояса |
| Википедия (`geosearch`), Nominatim (`search_amenity`) | ✓ 200 — досуг работает без ключей |
| `hotels_mock` | сервис ещё не написан |

Все нужные ключи получены.

### Выдуманные значения в примерах

Их надо заменить на настоящие, когда появятся данные:
- id отелей и `region_id 1001` — это наш мок;

### Не до конца подтверждено по официальной документации

- максимальный `limit` и лимиты запросов у Aviasales (поля ответа уже подтверждены реальным запросом: длительности в минутах, время с часовым поясом, цена туда-обратно);
- дневной лимит ключа Яндекса (смотреть в кабинете developer.tech.yandex.ru);

### Следующие шаги (из docs/providers/PLAN.md)

1. Smoke-скрипт с реальными запросами и сохранением ответов в `testdata/`.
2. Resolver (город → коды).
3. Builders (`TripRequest` → `RequestSet`).
4. HTTP-клиент с ретраями, лимитами и кэшем.
5. Нормализация ответов.
6. Сам `hotels_mock`.
7. Досуг на пересадках.
8. Офлайн-режим для защиты.

### Прочее

- **Атрибуция:** на фронтенде нужен футер с указанием источников (Яндекс.Расписания, Википедия CC BY-SA, OpenStreetMap, Open-Meteo).
- **Ночные поезда и рейсы:** дата заезда в отель — это дата *прибытия*. Всегда храним смещение часового пояса.

## 7. Для Сони: бесплатная LLM

**Рекомендация: GigaChat.** Физлицам дают бесплатные токены на 12 месяцев:

| Модель | Токены |
|---|---|
| Lite | 250 млн |
| Pro | 40 млн |
| Max | 25 млн |
| GigaChat-3-Ultra | 50 млн |

Этого хватит с запасом, гораздо больше 5–6 запросов на пользователя.

Ограничения:
- один запрос одновременно;
- один вызов функции за ответ;
- в OpenAI-совместимом API — старый формат `functions`;
- нужен корневой сертификат Минцифры.

Остальные варианты хуже:
- **Gemini** недоступен в России.
- **Groq** бесплатно даёт всего 8 тыс. токенов в минуту — мало для агента.
- **OpenRouter** даёт 50 запросов в день.
- **Cerebras и Yandex Cloud** больше не дают бесплатного доступа новым пользователям.

Если использовать **LiteLLM**: в версии 1.106.4 при передаче `tools` падает импорт отсутствующего пакета `mcp`, его нужно доставить отдельно (`pip install mcp`).
