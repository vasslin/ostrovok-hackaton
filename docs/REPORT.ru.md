# Что сделано: провайдеры путешествий и конфиги

**Ostrovok Hackathon 2026 · трек «О!дин запрос» · команда godnota**
Задача 2 (Даня Антонов): найти API провайдеров путешествий (билеты, отели, досуг во время поездки и пересадок), подготовить конфиги и описание API.
Дата описанного прогона: 2026-10-25. Исходный провайдерный код опубликован в ветке `providers-api` (на 2026-10-27 — commit `33be312`). Разделы с этой датой описывают исторический срез; новые локальные правки ниже ещё не закоммичены и не объединены с другими ветками.

### Локальные изменения для подготовки интеграции (2026-10-27)

- Добавлен публичный пакет `providerkit` как вход для других Go-модулей и `BuildTripPlan`: из `TripRequest` и отдельно разрешённых кодов/дат формируются карты `Discovery` и `Search` по имени провайдера. Результат содержит `Missing` и `Limitations`; клиент может не отправлять неполный или неподтверждённый поиск.
- Добавлены пример `ResolvedTrip` и CLI `go run ./cmd/maptrip` для воспроизводимого просмотра этих карт без сети. Сам resolver городов, выполнение запланированных HTTP-запросов и нормализация ответов отсутствуют.

- Удалены гостиничный mock, его 11 ручек, конфиги, примеры и структуры. В текущем дереве 10 провайдеров, 14 ручек/схем и 20 JSON-примеров, включая пять `TripRequest` и один `ResolvedTrip`.

### Отели

- В рамках этого исследования не получен доступный команде API отелей с актуальными ценами и бронированием. Проверенный тогда Hotellook вернул 404; ETG / RateHawk требует отдельного доступа.
- Бесплатный API с актуальными ценами и бронированием не найден. Hotellook недоступен; ETG / RateHawk документирован, но требует партнёрского договора и ключей.
- Ветка больше не содержит mock-контракт, фиктивные тарифы или ручки отелей. AI-конфиг сохраняет пожелания пользователя, а `BuildTripPlan` сообщает об отсутствии поставщика и не создаёт ложное предложение. Для подключения нужен отдельный адаптер по актуальной документации ETG.

## 3. Как устроены конфиги

Планируемый поток между сервисами описан в `ABOUT.md` на `origin/main`:

```text
текст пользователя → ai-service → TripRequest → валидация
                  → resolver городов → запросы по провайдерам
                  → HTTP-клиент → нормализованные предложения
                  → route-service → маршруты → frontend
```

На commit `33be312` реализованы `TripRequest`, проверка части правил, `RequestSet` как тип, реестр и сборка одного HTTP-запроса из готового провайдерного конфига. В текущей локальной копии появился `BuildTripPlan`, который строит `RequestSet` из `TripRequest` и переданного `ResolvedTrip`; он отделяет запросы для поиска кодов от поиска предложений. Автоматического resolver, HTTP-клиента с retry/кэшем, нормализации ответов и подключения к `provider-service` ещё нет. Единый конфиг должен содержать понятные человеку значения; коды провайдеров должны вычисляться проверенным кодом, а не приниматься из ответа модели без проверки.

**Планируемое правило уточнений:** `MissingRequired` возвращает пути незаполненных обязательных полей (например `/origin/city`). Оркестратор должен по ним выбирать короткий вопрос или форму, не переходя к поиску только потому, что общий процент заполнения превысил порог. Полный цикл вопросов и форма в этой ветке не реализованы.

### 3.1. Единый конфиг для AI-агента: `TripRequest`

Файл схемы: `configs/trip_request.schema.json`.

**Обязательные поля:**
- `schema_version`, `locale`, `currency`;
- `origin.city`;
- `dates` (`departure_date` **или** `departure_month`);
- `travelers.adults`.

**Остальные блоки:**
- `destination`: город или кандидаты. Пусто — режим вдохновения.
- `dates`: даты, число ночей, гибкость.
- `travelers`: взрослые, возраста детей, питомцы, гражданство.
- `transport`: виды транспорта, прямые рейсы, пересадки, время вылета.
- `hotel`: звёзды, питание, бесплатная отмена, цена за ночь, удобства, расположение.
- `leisure`: интересы, досуг на пересадках.
- `budget`.
- `ai_context`: «доп поле для валидации — определяет ИИ»: цель поездки, прогулочный район, события, must have / must avoid, допущения агента.

### 3.2. Конфиги для каждого API

1. **`configs/providers.json`:** реестр. Для каждого провайдера:
   - базовый URL;
   - авторизация: только *имена* переменных окружения, секретов в файле нет;
   - лимит запросов в секунду, таймаут, время кэша;
   - для каждой ручки: метод, путь, где параметры (`query` или `json`).
2. **`configs/examples/<провайдер>.<ручка>.json`:** конфиг запроса: ровно те параметры, которые уходят в HTTP-запрос, с именами полей как у провайдера.
3. **В коде:** `RequestSet map[string][]Request`, то есть «мапа [имя провайдера] → конфиги». Значение — срез, потому что одному провайдеру может понадобиться несколько вызовов (туда и обратно, поиск → страница отеля). В локальной копии `BuildTripPlan` заполняет эту мапу из `TripRequest` и `ResolvedTrip`; получение разрешённых кодов, выполнение запросов и разбор ответов остаются задачей интеграции.

### 3.3. Как помечены обязательные поля и ограничения формата

В примере запроса JSON обязательность полей не описана; для этого служит JSON Schema. В этой реализации источником схемы являются теги Go-структур:

- **Единственный источник правды — теги Go-структур:**
  ```go
  Origin string `json:"origin" url:"origin" validate:"required,len=3,alpha,uppercase" jsonschema:"required,pattern=^[A-Z]{3}$"`
  ```
  - `validate`: проверка в Go во время работы (библиотека go-playground/validator);
  - `jsonschema`: попадает в сгенерированную JSON Schema (библиотека invopop/jsonschema);
  - `url` / `json`: как поле отправляется (query-строка или тело JSON);
  - `path:"name"`: подставляется в `{name}` в пути ручки.
- **Схемы генерируются командой `go generate ./...`.** Их можно отдать:
  - Соне: LLM заполняет конфиг строго по схеме;
  - Василине: для описания ручек;
  - Дане Казановичу: форма для недостающих полей.
- **Правила, которые не выразить тегами**, написаны кодом:
  - `TripRequest.ValidateAt`: возвращение после отъезда, не больше 30 ночей, дата не в прошлом и не дальше 365 дней;

### 3.4. Шпаргалка по форматам провайдеров

Это правила, заложенные в конфиги и валидаторы текущей ветки. Для живой интеграции сверяйте их с действующей документацией API и ответом конкретной ручки.

| Что | Правило |
|---|---|
| Даты в запросах | `YYYY-MM-DD`; Aviasales принимает ещё `YYYY-MM` |
| Дата-время в ответах | ISO 8601 со смещением (смещение не терять!), отмена в ETG — UTC |
| IATA | 3 заглавные буквы `^[A-Z]{3}$` |
| Коды Яндекса | город `c213` (Москва), станция `s9600213` |
| Страна | ETG `residency` строчными (`ru`), Travelpayouts `country_code` заглавными (`RU`) |
| Валюта | Aviasales строчными (`rub`), ETG заглавными (`RUB`) |
| Координаты | lat −90..90, lon −180..180; **в OSRM порядок `lon,lat`** |
| Гости в отеле | до 9 номеров; 1–6 взрослых на номер; до 4 детей 0–17 лет на номер |
| Проживание | заезд не позже чем через 730 дней; выезд не позже 30 дней после заезда |
| Хэши ETG | `hash` 1–256 символов, живёт 24 ч; `search_hash` живёт 38 мин; `partner_order_id` — UUID |
| Пагинация | Яндекс `limit` ≤100; Nominatim `limit` ≤40 |
| Погода | прогноз до 16 дней; морской прогноз 0–8 дней; история с 1940 (море с 2022) |

### Что проверяют тесты

- Каждый пример проходит и Go-теги, и свою JSON Schema, и превращается в правильный HTTP-запрос.
- URL собирается правильно для Aviasales (query + заголовок), Яндекса (ключ в query), OSRM (подстановка в путь), Википедии и для POST с JSON к отелям.
- 16 неверных значений отклоняются, например:
  - IATA строчными;
  - 7 взрослых в номере;
  - 5 детей в номере, ребёнок 18 лет;
  - проживание больше 30 ночей;
  - `residency` заглавными;
  - не-UUID в `partner_order_id`;
  - ребёнок-гость без возраста;
  - `limit` Nominatim больше 40.
- 11 ошибок в `TripRequest` отклоняются: возвращение раньше отъезда, дата в прошлом, 10 взрослых, неизвестный транспорт и т.д.
- `MissingRequired` возвращает правильные пути.
- `providers.json` совпадает с каталогом в Go.
- Схемы на диске актуальны: тест падает, если поменяли структуру и забыли `go generate`.

Отдельно проверено, что тесты действительно ловят ошибки. Если специально испортить пример (`"origin": "mow"`), падают обе проверки: схема (`'mow' does not match pattern '^[A-Z]{3}$'`) и теги Go.

## 5. Как пользоваться

Нужен Go 1.26+:

```bash
brew install go
```

После изменения любой структуры:

```bash
go generate ./...
```

Проверить всё:

```bash
go test ./...
```

Пример в коде:

```go
reg, _ := providers.LoadRegistry("configs/providers.json")
req, err := reg.NewHTTPRequest(ctx, providers.Request{
    Provider: "aviasales", Endpoint: "prices_for_dates",
    Params: &providers.AviasalesPricesForDates{Origin: "MOW", Destination: "KZN", DepartureAt: "2026-12-12", Currency: "rub"},
})
```

Секреты задаются переменными окружения:
- `TRAVELPAYOUTS_TOKEN`
- `YANDEX_RASP_API_KEY`

Ключи ETG в этой ветке не настроены.

**Добавить новую ручку:**
1. Написать структуру с тегами в `internal/providers/`.
2. Добавить её в `Catalog`.
3. Добавить ручку в `providers.json`.

## 6. Что ещё не сделано и на что обратить внимание

### Ключи и проверка настоящими запросами

Утилита `go run ./cmd/smoke` отправляет примеры в настоящие API при наличии соответствующих ключей окружения и сохраняет ответы в `testdata/`. Перед повторным прогоном проверьте, что запросы и сохранённые ответы не содержат секретов или персональных данных.

Прогон 2026-10-25:

| Провайдер | Результат |
|---|---|
| Aviasales (`prices_for_dates`) | ✓ 200, реальные рейсы Москва → Казань на 12–14 декабря |
| Travelpayouts places, Nominatim, OSRM, Open-Meteo (прогноз, история, море), ЦБ | ✓ 200 |
| Яндекс.Расписания | ✓ 200 со вторым ключом (первый так и не активировался). Поиск: 10 поездов Москва → Казань на 12 декабря, **ни у одного нет цены** — цены на поезда берём из `transport_mock`. Код Казани `c43` подтверждён. В `thread` время остановок приходит в другом формате: `2026-12-12 20:40:00`, без часового пояса |
| Википедия (`geosearch`), Nominatim (`search_amenity`) | ✓ 200 в историческом пробном запросе; `search_amenity` исключён из массового поиска мест из-за правил публичного Nominatim |
| Отели | не настроен: ETG / RateHawk требует договора и отдельного адаптера |

Для отельного API рабочего доступа в этой ветке нет. Настоящий ETG требует отдельного договора, HTTPS-адаптера и учётных данных.

### Синтетические значения в примерах

Примеры запросов — фиксированные входные данные для воспроизводимости, а не актуальные предложения или цены. Гостиничных id и цен в конфигурациях провайдеров больше нет: источник отелей не подключён.

### Не до конца подтверждено по официальной документации

- максимальный `limit` и лимиты запросов у Aviasales (поля ответа уже подтверждены реальным запросом: длительности в минутах, время с часовым поясом, цена туда-обратно);
- дневной лимит ключа Яндекса (смотреть в кабинете developer.tech.yandex.ru);

### Следующие шаги (из docs/providers/PLAN.md)

1. Resolver (город → коды) с обработкой одинаковых названий и часовых поясов.
2. Расширение `BuildTripPlan` для многогородских маршрутов и досуга на пересадках после получения реальных сегментов.
3. HTTP-клиент с тайм-аутами, ограниченными повторами, лимитами и кэшем.
4. Нормализация ответов с источником, валютой, временем получения и признаком синтетических данных.
5. Доступ к реальному API отелей и адаптер; досуг на пересадках с проверкой времени.

- **Атрибуция:** на фронтенде нужен футер с указанием источников (Яндекс.Расписания, Википедия CC BY-SA, OpenStreetMap, Open-Meteo).
- **Ночные поезда и рейсы:** дата заезда в отель — это дата *прибытия*. Всегда храним смещение часового пояса.

## 7. Совместимость с AI и критерий выбора модели

Ветка `origin/ai-service` использует собственный плоский конфиг и отдельный gRPC-контракт. Для интеграции нужно согласовать их с вложенным `TripRequest`, проверкой обязательных полей и протоколом ошибок. Доступность модели, бесплатная квота и условия конкретного аккаунта меняются; их следует проверять на дату развёртывания, измерив 30–40 реальных запросов в сутки и типичный диалог из 5–6 вызовов на пользователя. Исторические оценки квот без такого прогона не используются как доказательство готовности.
