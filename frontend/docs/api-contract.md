# Контракт браузера с gateway

Текущий адаптер реализован в `dist/api.js`. Браузер обращается только к gateway, без ключей AI и провайдеров. Внутренние proto/gRPC-контракты сервисов команда может проектировать независимо.

Базовый путь `/api`. JSON UTF-8. Ответы без дополнительных обёрток `data`. Полный пример объекта поездки - `dist/assets/demo-trip.json`; типы - `docs/contracts.d.ts`.

| Метод и путь | Тело запроса | Ответ |
|---|---|---|
| `POST /chat/messages` | `{ tripId: string \| null, text: string, criteria: Criteria \| null }` | `{ trip: Trip \| null, message: string, actions: [{label, value}] }` |
| `PATCH /trips/:id/selection` | `{ type: "hotel" \| "ticket", itemId, offerId, revision }` | `{ trip: Trip }` |
| `POST /trips/:id/bookings` | `{ revision: number, demo: true }` | `{ booking: Booking, trip: Trip }` |
| `GET /me` | - | `{ profile: {name, email, phone} }` |
| `PATCH /me` | `{name, email, phone}` | `{ profile: {name, email, phone} }` |
| `GET /me/trips` | - | `{ trips: [{booking, trip}] }` |
| `GET /trips/:id` | - | `{ trip: Trip }` |

## Как связываются экраны

1. Пользователь отправляет сообщение. Gateway возвращает ответ помощника и целиком обновлённую поездку. Если нужен уточняющий вопрос, `trip` может оставаться `null` или содержать предыдущий план, `message` содержит вопрос, `actions` - возможные ответы.
2. `stops` - вершины графа; `segments` - рёбра. Порядок остановок - порядок поездки, повторное посещение города имеет отдельный `id`.
3. При выборе отеля `itemId` - ID остановки, `offerId` - ID варианта из `hotelOptions`. Для билета - ID сегмента и вариант из `options`.
4. Backend возвращает подтверждённый выбор, новый `revision`, всю поездку и авторитетный расчёт суммы. Фронт не применяет к итоговой цене собственные скидки.
5. Оформление создаёт только демозаказ. Для будущих реальных покупок нужен отдельный согласованный контракт и платёжный процесс.

## Правила полей

- Все суммы - целые числа в копейках. `12562000` означает 125 620 ₽. Валюта текущего прототипа - RUB.
- `Ticket.priceMinor` - за всех пассажиров; `Hotel.priceMinor` - за все номера и ночи. Эти поля можно складывать.
- `totalMinor = transportMinor + hotelsMinor + transferMinor + activitiesMinor`.
- Даты поездки - `YYYY-MM-DD`; время транспорта - ISO 8601 с часовым поясом, например `2026-11-10T08:00:00+03:00`. UI показывает местное время из строки, длительность считает по UTC.
- Координаты WGS84: `lat` от -90 до 90, `lng` от -180 до 180. Они обязательны для каждой остановки.
- `hotel` входит в `hotelOptions`, `ticket` - в `options`. У точки отправления и возвращения `hotel: null` и `nights: 0`.
- `warnings` - предупреждения, включая превышение ограничений и непосчитанные доплаты.
- Текущий UI поддерживает авиаперелёты. Для поездов, паромов и автобусов сначала расширьте `Ticket.type`, карточки и подписи.
- `cover` выбирает локальную иллюстрацию, а не фотографию реального отеля.

## Ошибки и повторные запросы

Ответ с HTTP 4xx/5xx: `{ "message": "Понятное пользователю описание", "code": "OPTION_UNAVAILABLE" }`.

- 400/422 - неверные параметры: показать объяснение, сохранить введённое сообщение.
- 409 - устаревшая ревизия/вариант недоступен: вернуть понятное сообщение; повторное получение актуальной поездки можно добавить в адаптер.
- 429 - исчерпана квота AI: сообщить об этом, не обнулять маршрут.
- Тайм-аут фронта - 20 секунд. Можно повторить запрос через чат.
- Бронирование передаёт заголовок `Idempotency-Key`. Backend обязан возвращать тот же заказ при повторении ключа и не создавать дубликаты.
- Авторизацию предоставляет backend. В демо настоящего входа нет. При отдельном домене нужен согласованный CORS и механизм сессии; текущий адаптер использует `credentials: same-origin`.
